# Decisions

Every place the port departs from the original, or the BBC forces a choice
the original never had to make. Numbered, dated, with the reason. A decision
is only reversed by a new row that says why.

| # | Date | Decision | Why |
|---|---|---|---|
| 1 | 2026-10-04 | **Screen: MODE 1 pixels, CRTC narrowed to 256 x 192** (64 columns x 24 rows, 12K at `&5000`) | The Spectrum's exact geometry, pixel for pixel, so the map and every graphic carry over unscaled. MODE 2's 8 colours would cost half the horizontal resolution (160 pixels can't hold 256), and the one-pixel ropes and brick patterns are the look of the game. MODE 1's pixels are close to the Spectrum's shape. 12K instead of 20K, and 512-byte rows make the address arithmetic cheap. How to fit the colours into four is decision 2, still open. |
| 2 | 2026-10-04 | **Colour: four colours per room**, chosen offline (`tools/mkrooms.py`): logical 0 is the room's background paper, the other three the colours covering the most pixels, and every Spectrum colour mapped to one of the four by brute force, keeping ink and paper distinct in every cell the room draws and every colour distinct from the background | Measured on the oracle's pixels: 98.8% of playfield pixels show in their own colour on average (worst room 91.4%). Changing the palette every character row would reach 99.95%, but needs an interrupt every 8 lines landing in a 64-cycle horizontal blank, and sprites would change colour from row to row. Revisit for the worst rooms if they look wrong in play. |
| 3 | 2026-10-04 | **Target: a stock BBC Model B** (32K, DFS). Sideways RAM, or a Master, only if it truly cannot fit, and then as a new row here | Matt's call: "try to fit this in a beeb first". The original is ~38K of code and data against ~19K free beside a 12K screen, so this shapes everything: room data packed and unpacked a room at a time, graphics kept 1bpp and coloured as they are drawn, front-end text off the critical path. |
| 4 | 2026-10-04 | **Text in the BBC's own font**, read from the MOS ROM at `&C000`, not the Spectrum ROM's | The Spectrum's text is its ROM font (`CHARS = &3C00`), which isn't ours to copy, and reading the MOS's costs no RAM. The room texts ("BEWARE OF THE DOG") and the status bar look a little different. |
| 5 | 2026-10-04 | **Rooms packed as bit streams**, one per room, unpacked into the original's bytecode when a room is entered (`tools/packrooms.py`, `src/unpack.6502`) | 13,633 bytes of room data become 7,770, saving 5.9K of a Model B (decision 3). LZ didn't see the structure: per-room ZX02 reached 10,220, 9,671 with a shared dictionary. The packing is a prefix code per command class, move-to-front lists for attribute, tile and type (they repeat from one record to the next ~80% of the time), and fixed widths for position and length, which are near-incompressible (4.2-5 bits of entropy each). Unpacking to the original bytes keeps the verified drawer unchanged. One run (room 33) gives column 32, which the original's arithmetic makes row 12 column 0; it is packed as that. |
| 6 | 2026-10-04 | **Yellow is one of every room's four colours** | Harry is yellow on the Spectrum in every room; with decision 2 alone room 1's palette had no yellow and he'd have been white there. Costs about a point: 97.8% of playfield pixels in their own colour on average (98.8% before), worst room 83% (room 5, whose white pipes turn yellow). |
| 7 | 2026-10-04 | **Keys are the Spectrum's for now**: Q up, A down, O left, P right, 1 take/drop, 0 abort, S save; SPACE jumps, standing in for SYMBOL SHIFT, which sits beside SPACE on a Spectrum | Matt: "the spectrum ones work and are authentic"; BBC-appropriate defaults are for later discussion (`docs/for-review.md`). Internal key numbers measured in jsbeeb (1 = 48, 0 = 39; Q = 16 and SPACE = 98 agree with the port kit's table). |
| 8 | 2026-10-04 | **Target revised: a BBC Model B with 16K of sideways RAM** (or a B+128, or a Master). Revises decision 3 | A stock Model B was tried first, as Matt asked, and the numbers say no: with the rooms packed there are 4.5K free under the screen, perhaps 6K with OS pages scavenged, and the rest of the game needs about 20K (Spectrum sizes: monster and machine graphics 7.5K, object sprites 1.3K, monster tables 1.2K, Harry 3.1K, monsters' code 2.7K, objects and machines' logic, sound, the in-play front end; `docs/memory-map.md`). The only stock-B route would be loading every room's data from disc as you enter it: pauses and drive noise on every screen. Sideways RAM was Matt's stated fallback; it is the port kit's baseline machine too. One bank holds the data and stays paged in, so the code reads it at `&8000` like any other memory. |
